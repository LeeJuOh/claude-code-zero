# Orientation Guide

How to explore a repo and generate `orientation.md`. Read this when running `/duck orient` and no existing orientation file is found (or when regenerating with `/duck orient refresh`).

Exploration methodology adapted from [learning-opportunities](https://github.com/DrCatHicks/learning-opportunities) by Dr. Cat Hicks (CC-BY-4.0), drawing on program comprehension research by Spinellis (2003), Hermans (2021), and Storey et al. (2006).

---

## Exploration Sequence

Experts read code **strategically and selectively**, not exhaustively. Follow this sequence to build a mental model of structure.

### 1. Detect languages

Check for manifest/config files at the project root:

| Language | Signal files |
|:---------|:-------------|
| Python | `pyproject.toml`, `setup.py`, `requirements.txt`, `Pipfile` |
| JavaScript | `package.json` (no `tsconfig.json`) |
| TypeScript | `package.json` + `tsconfig.json` |
| Go | `go.mod` |
| Rust | `Cargo.toml` |
| Ruby | `Gemfile`, `*.gemspec` |
| Java/Kotlin | `pom.xml`, `build.gradle`, `build.gradle.kts` |
| C/C++ | `CMakeLists.txt`, `configure.ac`, root-level `Makefile` |
| C# | `*.csproj`, `*.sln` |
| R | `DESCRIPTION`, `NAMESPACE`, `*.Rproj` |

Read each detected manifest file — it contains declared purpose, dependencies, entry points, and scripts.

### 2. README and top-level docs

Read `README.md` (or `README.rst`, `README`). Check for a `docs/` directory — read its index if present. This gives the stated purpose and intended audience.

### 3. Directory tree

Run `find . -maxdepth 3 -not -path '*/.git/*' -not -path '*/node_modules/*' -not -path '*/__pycache__/*' -not -path '*/.venv/*' -not -path '*/vendor/*'` to get the top-level structure. Directory naming conventions (`src/`, `lib/`, `tests/`, `cmd/`, `pkg/`) reveal architecture before any code is read.

### 4. Entry points

Identify and read based on detected language:

- **Python**: `__main__.py`, `cli.py`, `main.py`, or `[project.scripts]` in `pyproject.toml`
- **JavaScript/TypeScript**: `main` field in `package.json`, `index.js`, `src/index.ts`
- **Go**: `cmd/*/main.go` or root `main.go`
- **Rust**: `src/main.rs` or `src/lib.rs`
- **Ruby**: `bin/`, `lib/<gem-name>.rb`
- **Java/Kotlin**: class with `public static void main` or Spring Boot `@SpringBootApplication`

### 5. Test files

Read 2-3 test files, prioritizing integration or end-to-end tests over unit tests. Tests are executable specifications — reading test names and assertions is one of the fastest ways to understand what a module does.

### 6. Core modules

Identify the 5-8 most important source files based on what you've learned. Read their top-level structure (class/function names, imports, docstrings) without reading every implementation in full.

### 7. Git history (if available)

Run `git log --oneline -20` for recent activity. Run `git log --format="%f" | sort | uniq -c | sort -rn | head -10` to identify most-edited files — high-churn files are usually the core of the system.

## orientation.md Template

Write to `.claude/orientation.md` using this exact structure:

```markdown
# Repo Orientation: [repo name]

> Generated by /duck orient. Re-run with `/duck orient refresh` to update.

## One-line purpose
[Single sentence: what this repo does and why it exists.]

## Primary language(s)
[List languages detected, dominant one first.]

## Pipeline / workflow stages
[Ordered list of the main stages data or requests flow through. One line each.
If no pipeline, describe the main modules and their relationships.]

## Key files
[6-10 entries:]
- `path/to/file` -- [what it does] | [why a new developer should read it]

## Core concepts
[3-5 domain or architectural concepts essential to working in this codebase:]
**[Concept name]**: [Plain-English definition. Where in the code it lives.]

## Common gotchas
[2-3 things that commonly trip up new developers. Be specific -- reference actual file paths or function names.]

## Suggested exercise sequence
[EXACTLY 2 exercises following these rules:

Good orientation exercises direct the learner to read one specific, short artifact,
then ask them to synthesize or explain what they read:
- "Open README.md and read the Features section. Then close it and explain to a
  non-developer what this tool produces and why someone would use it."
- "Open `models.py`. Find the main dataclass. What fields does it have, and what
  does that tell you about the pipeline's stages?"

Bad orientation exercises (save for later sessions):
- "Without opening any files, predict the pipeline stages" -- no basis for this
- Predicting specific function outputs or algorithmic behavior
- Tracing through individual method implementations
- Debugging specific logic

For each exercise: specify the exact file to open, what to read, and what
synthesis question to answer after reading.]

## Sources consulted
[List the files and paths actually read while generating this file.]
```

Keep each section concise. This is a teaching scaffold, not documentation. Prioritize clarity over completeness.
